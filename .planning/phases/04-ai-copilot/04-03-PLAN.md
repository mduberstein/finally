## Phase Goal

**As a** trader running a simulated portfolio, **I want to** converse with an AI assistant that analyzes my portfolio and acts on it through natural language, **so that** I can ask questions and place trades in plain English instead of reading tables and filling in forms.

<objective>
Make the assistant actually know the portfolio and actually act on it: every turn carries live cash, positions, P&L, concentration, and the watchlist into the prompt, and every trade or watchlist change the assistant returns executes immediately through the existing service functions, with each outcome captured and each refusal explained in exact numbers.

Purpose: CHAT-02, CHAT-03, CHAT-04, and CHAT-05 — the four requirements that turn Plan 01's round-trip into a copilot. Everything here is glue over domain logic Phases 2 and 3 already shipped and tested; the only genuinely new logic is context assembly, the sequential execution loop, and the rejection-to-sentence mapping.
Output: `build_portfolio_context`, the action-authorized system prompt, the execution loop inside `handle_chat_message`, and an `LLM_MOCK` mock that can drive an action deterministically.
</objective>

**Execution loop — `execute_actions(response, cache) -> tuple[list[dict], list[str]]` in `backend/app/chat/service.py`.**
Returns the action-payload list and the list of explanation sentences the failures produced. Iterate `response.trades` then `response.watchlist_changes`, one at a time, each inside its own `try` / `except`. Never batch, never hold a state snapshot across actions: `execute_trade` re-reads cash and position state on every call inside its own `BEGIN IMMEDIATE` transaction, which is exactly what makes two trades in one turn compose correctly when the first spends the cash the second wanted (04-RESEARCH.md Pitfall 4). A failure appends its outcome and its sentence and the loop continues to the next action — a turn that proposes three things and fails one must still report the two that worked.

For each trade: guard the quantity first — it must be a positive whole number, which is D-09 expressed at the boundary rather than only in the schema; a value failing that guard is recorded as a failed action with the invalid-trade code and never reaches `execute_trade`. Otherwise call `execute_trade(ticker, side, quantity, cache)` and record an executed element carrying the ticker, side, quantity, and the returned fill price. Catch `TradeRejected` and record a failed element carrying the ticker, side, quantity, and the exception's `code`.

For each watchlist change: call `add_ticker(ticker)` or `remove_ticker(ticker)` by the element's action field. An add records an executed element; a `WatchlistRejected` records a failed element with the exception's code. A remove that returns False changed nothing, so record it as a failed element with a not-on-watchlist code rather than as executed — `04-UI-SPEC.md` Discretion resolution 4 makes an executed element mean a card appears, and a card must never claim something that did not happen.

Do not re-validate cash, share ownership, ticker shape, or the watchlist cap here. Those checks live in `execute_trade`, `normalize_ticker`, and `add_ticker` and are already tested; duplicating them creates two places for the rules to drift. Issue no SQL from this module against `positions`, `trades`, `users_profile`, `portfolio_snapshots`, or `watchlist` — the only table this package writes is `chat_messages`.

**Rejection copy — `rejection_sentence(error) -> str` in the same module.**
A pure function mapping a `TradeRejected` or `WatchlistRejected` to one plain-language sentence carrying the exact numbers from its `detail()` payload, mirroring server-side what `frontend/lib/trade.ts`'s `tradeErrorMessage` does client-side. Per D-06 each sentence states the fact and the limit with real figures: an unaffordable buy names the ticker, the trade's cost, and the available cash; an oversell names the ticker and the owned quantity; an untradable ticker names the ticker and says it has no live price; a duplicate add names the ticker and says it is already on the watchlist; a full watchlist names the limit; an invalid ticker names the offending symbol; an absent removal names the ticker and says it was not on the watchlist. Format money with a thousands separator and two decimals. Use a `switch`-equivalent dispatch on the exception's `code` with a neutral fallback for an unrecognised one, exactly as `tradeErrorMessage` does — never render a raw exception string into user-facing text.

**Turn handling — `handle_chat_message`.**
Between parsing and persisting, call `build_portfolio_context(cache)` and pass it into `build_messages`, then run `execute_actions` on the parsed response. Join the returned explanation sentences onto the assistant's own message text — a blank line between the model's prose and the appended explanations — before persisting and returning. This is how D-06's exact numbers reach the user: the model composed its reply before any action ran, so it cannot know what was refused, and `04-UI-SPEC.md`'s Copywriting Contract commits the backend to constructing that text. Persist the combined message and the full action list on the assistant row; return `{"message": <combined>, "actions": <list>}`, the same keys Plan 01 established and Plan 02's panel already consumes.

## Flagged assumptions

Recorded rather than silently decided.

1. **Failure explanations are constructed by the backend, not by a second model call** (CHAT-05 probe, unclassified). The model composes its reply before any action runs, so it cannot know what was refused. `04-UI-SPEC.md`'s Copywriting Contract already commits the backend to constructing this text and the frontend to rendering it as an ordinary assistant bubble. Assumption: a deterministic `rejection_sentence` mapping appended to the model's message, rather than a round-trip that would double latency and cost for every refusal.
2. **A watchlist remove of an absent ticker is a failed action, not a success** (CHAT-04 idempotency probe). `remove_ticker` itself is idempotent by design and raises nothing. Assumption: report it as non-executed so Plan 04 renders no card, because `04-UI-SPEC.md` Discretion resolution 4 makes a card mean "it happened."
3. **Concurrency guarantee** (CHAT-04 concurrency probe). Assumption: a chat turn and a manual trade cannot interleave destructively, because `execute_trade` re-reads cash and position state inside its own `BEGIN IMMEDIATE` transaction on every call and the chat loop holds no snapshot across actions. Marked as a backstop truth rather than an explicit one — the existing threaded concurrent-trade test from Phase 2 covers the transaction, but no test drives a chat turn and a manual trade simultaneously.
4. **Portfolio analysis is available on every turn, not only when asked** (CHAT-02 probe, unclassified). Assumption: the context block is always present in the system prompt, and D-07's reactive-only constraint governs whether the assistant volunteers anything with it. Always including it costs a small fixed number of tokens and removes the need for the model to request data mid-turn.
5. **Auto-execution has no confirmation of any kind** (CHAT-03 probe, unclassified). Assumption: `planning/PLAN.md` section 9's explicit "no confirmation dialog" applies unconditionally, matching the manual trade bar and watchlist removal.
6. **`LLM_MOCK` mock reacts to instruction-shaped phrasing** (04-RESEARCH.md assumption A2). Assumption: a small deterministic pattern match is required, because without it CHAT-03 and CHAT-04 cannot be exercised in CI or in Phase 5's E2E suite, both of which run with the mock on.
7. **Concentration is reported as the largest position's share of total value.** No source artifact defines the metric. Assumption: largest-position weight, because it is the same figure the heatmap already sizes rectangles by, so the chat answer and the visualization agree.
