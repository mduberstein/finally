**Harness contract from Plan 03.** `test/playwright.config.ts` sets `testDir` to `./e2e`, `workers: 1`, `fullyParallel: false`, and a `baseURL` from the environment. Specs run in numeric filename order against one shared app container backed by one SQLite database. The canonical run command is recorded verbatim in `05-03-SUMMARY.md` — use exactly that, including any teardown step it found mandatory.

**State discipline across specs.** `01-fresh-start.spec.ts` asserts a pristine database: cash text `10,000.00`, ten default tickers, and the positions empty state. It runs first. Every later spec therefore runs against a database the earlier ones have already mutated, and must (a) restore whatever it can, and (b) never assert an absolute figure that an earlier spec could have changed. `02` adds a ticker and removes it, netting to zero. `03` buys and sells back, netting to approximately zero cash and exactly zero position. `04` deliberately leaves a small position behind — that is fine, because nothing after it asserts an empty positions table.

**Locators that exist in the shipped frontend.** There are no `data-testid` attributes anywhere in `frontend/`, and Plan 03 established that none will be added:
- Watchlist panel: a `section` whose `h2` is `Watchlist`
- Per-ticker handle: a `button` whose accessible name is exactly `Remove AAPL from watchlist` (substitute the ticker). This is the only reliable per-ticker locator; plain text matching breaks on the single-letter ticker `V`
- Add form: input `#watchlist-add-ticker` (placeholder `Ticker`, Enter also submits), button labelled `Add`. `frontend/components/WatchlistAddForm.tsx` shows an inline `role="alert"` on failure
- Trade bar: input `#trade-ticker` (placeholder `AAPL`), input `#trade-quantity` (placeholder `10`, `inputMode` numeric), buttons labelled `Buy` and `Sell`. Both buttons disable while a submit is in flight. `frontend/components/TradeBar.tsx` shows an inline `role="alert"` on rejection
- Positions panel: a `section` whose `h2` is `Positions`; empty state heading text `No open positions`; a populated row renders the ticker, then quantity, avg cost, price, unrealized P&L, and change percent as right-aligned cells
- Heatmap panel: a `section` whose `h2` is `Heatmap`; each cell carries a `title` attribute of the exact form `AAPL — 12.3% of portfolio, ...` (`frontend/components/HeatmapCell.tsx` line 25), which makes `getByTitle` with a regex a clean per-ticker locator
- Header: labels `Cash` and `Total Value`, each followed by a formatted number
- Connection indicator: `role="status"` whose text is exactly `Connected`, `Reconnecting`, or `Disconnected` (`frontend/lib/connection.ts` `statusLabel`)
- Chat panel: input with placeholder `Ask about your portfolio, or tell me to trade...`, button labelled `Send`. Assistant and user messages render as bubbles; an executed action renders a `ChatActionCard`

**Number formatting.** `frontend/lib/format.ts` `formatPrice` returns a grouped two-decimal string with NO currency symbol — `10,000.00`, not `$10,000.00`. `formatPercent` adds an explicit sign except on exact zero. Parse header figures by stripping commas before comparing numerically.

**Mock LLM behavior** (`backend/app/chat/llm.py` `mock_response`, deterministic, no network):
- The trade pattern is buy-or-sell, whitespace, a digit run, an optional "shares of", then a one-to-ten-letter ticker. The message `buy 2 AAPL` produces reply text `Mock: buy 2 AAPL.` and one trade action.
- Quantity must be a whole digit run — the pattern does not match decimals.
- Anything unmatched produces `Mock response: portfolio and watchlist unchanged.` with no actions.

**Executed-action payload** (`backend/app/chat/service.py` lines 127-132): `type` of `trade`, `status` of `executed`, plus `ticker`, `side`, `quantity`, `price`.

**Action card text** (`frontend/lib/chat.ts` `actionCardText`): an executed buy renders as a check glyph, then `Bought`, the quantity, the ticker, an at-sign, a dollar sign, and the formatted price. An executed sell uses `Sold`. A watchlist add renders `Added <TICKER> to watchlist`. The card renders only when `status` is executed, so its presence is itself proof the trade actually happened. Assert on a regex over the verb, quantity, and ticker rather than the whole string, so price formatting cannot make the test brittle.

**Connection-state machine** (`frontend/lib/connection.ts`): the indicator goes `Connected` on an EventSource open or any message; each error increments a counter and shows `Reconnecting` until three consecutive errors, at which point it shows `Disconnected`; a `connected` state with no message for 10 seconds downgrades to `Reconnecting`. Taking the context offline therefore produces `Reconnecting` first and possibly `Disconnected` after several retry cycles — assert only that the text is no longer `Connected`, never which of the two other labels appears, because that depends on the browser's EventSource retry timing.

**Trade side effects to expect.** A buy through the trade bar posts to `/api/portfolio/trade`, which executes and writes a portfolio snapshot inside `execute_trade()` itself. The page refetches the portfolio after a successful trade, so cash, positions, and heatmap all update without a reload.

**Fractional-sell edge already fixed.** Quick task `260817-mlm` replaced an exact float zero comparison in `_apply_sell` with an epsilon threshold, so selling a whole position closes the row rather than leaving a near-zero ghost. The trade spec's "position row disappears after selling everything" assertion depends on that fix and is a useful regression guard for it.

**Environment note for the executor:** the agent Bash sandbox denies the Docker daemon socket. Every `docker` and `docker compose` invocation must run with `dangerouslyDisableSandbox: true`.

<flagged_assumptions>

This is a deliberate, documented design, but it means renaming a spec file or enabling parallelism silently breaks the suite. Flagged so it is a known property rather than a trap.

2. **The offline-emulation reconnection test proves the client's recovery, not the server's.** Playwright's context-level offline control severs the browser's network, which exercises `frontend/lib/connection.ts`'s error handling and EventSource's own retry. It does not exercise what happens when the server drops the connection or restarts mid-stream. That stronger case would require Docker control from inside the test container and is out of scope here. Surfaced rather than claimed as covered.

3. **Timeout values in the reconnection spec are derived, not measured.** The 10-second staleness threshold and the three-error disconnect threshold come from `frontend/lib/connection.ts`; the browser's EventSource retry interval is a Chromium implementation detail this plan does not pin. The generous timeouts are reasoned from those constants, and the three-consecutive-run gate is what actually validates them.
