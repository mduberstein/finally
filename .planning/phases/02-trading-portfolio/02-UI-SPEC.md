## Design System

| Property | Value |
|----------|-------|
| Tool | shadcn (already initialized in Phase 1 — `frontend/components.json` exists) |
| Preset | style: `base-nova`, base color: `neutral`, CSS variables mode, no prefix |
| Component library | base-ui (`@base-ui/react`) primitives, wrapped by shadcn — **not** Radix; Phase 1's UI-SPEC anticipated Radix, but the actual `npx shadcn init` run used the `base-nova` style, which ships base-ui primitives (see `frontend/components/ui/button.tsx`'s `@base-ui/react/button` import). Correcting the record here for Phase 2 onward. |
| Icon library | lucide-react (`lucide-react` in `package.json`; unused so far, first candidate use is a small ticker/quantity input affordance if needed — plain text labels are the default per this phase's Copywriting Contract, icons are optional polish, not required) |
| Font | Inter (`next/font/google`, `--font-sans`), `font-variant-numeric: tabular-nums` (`.numeric` utility) on every price/cost/P&L cell — unchanged from Phase 1 |

No re-initialization needed. This phase adds one new shadcn primitive on top of the existing `button` and `skeleton`:

- `npx shadcn add input` inside `frontend/` — for the trade bar's ticker and quantity fields.

The positions table and trade bar follow Phase 1's established pattern of hand-built `<div>` grid rows (see `WatchlistRow.tsx`'s `WATCHLIST_ROW_GRID` constant) rather than the shadcn `table` primitive — Phase 1 never actually adopted `table`/`card`/`badge` despite anticipating them; it built `Watchlist.tsx`/`WatchlistRow.tsx`/`PriceCell.tsx` as plain styled `<div>`s. Phase 2 continues that established convention for consistency: a `PositionsTable`/`PositionRow` pair mirroring `Watchlist`/`WatchlistRow` exactly (grid template constant, skeleton-row loading state, empty-state block).

## Typography

Unchanged from Phase 1 — same four roles, same two weights. No new size or weight introduced this phase.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label | 12px | 400 (regular) | 1.5 |
| Body | 14px | 400 (regular) | 1.5 |
| Heading | 18px | 600 (semibold) | 1.2 |
| Display | 24px | 600 (semibold) | 1.2 |

Usage in this phase:
- **Label** — positions-table column headers ("TICKER", "QTY", "AVG COST", "PRICE", "UNREAL P&L", "CHG %"), trade-bar field labels ("Ticker", "Quantity"), header's "Cash" caption.
- **Body** — trade-bar input text, inline trade error text, positions-table secondary cells (qty, avg cost, % change).
- **Heading** — section titles ("Trade", "Positions").
- **Display** — header total portfolio value (most prominent number in the header, same visual weight as the Phase 1 watchlist price cell), positions-table's current-price and unrealized-P&L cells (the two numbers a trader scans first).

Only weights 400 and 600 exist. Do not introduce 500 or 700.

## Color

Unchanged 60/30/10 split from Phase 1; this phase **exercises** the Purple token that Phase 1 reserved but never used.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#0d1117` | Page background, main content area (unchanged) |
| Secondary (30%) | `#161b22` | Panel/card backgrounds (trade bar, positions table); borders `#30363d` (unchanged) |
| Accent (10%) | `#209dd7` (Blue Primary) | Unchanged Phase 1 reservations only: header wordmark, watchlist row hover/selected stripe, keyboard-focus ring. **Not** used on any Phase 2 element. |
| Destructive | `#dc2626` | No true destructive action exists this phase (trades are reversible market orders, no confirmation dialog by design — PLAN.md §3, D-04). The shadcn `destructive` button variant stays unused. |

Accent reserved for: header wordmark text color, watchlist row hover/active left-border stripe, keyboard-focus outline ring. Unchanged from Phase 1 — Phase 2 introduces no new accent (blue) usages.

**Purple Secondary `#753991`** (PLAN.md §2, "submit buttons") — first exercised in this phase:

| Element | Treatment |
|---------|-----------|
| Buy button | Filled, `background: #753991`, white/`--primary-foreground`-equivalent text. The trade bar's primary submit action. |
| Sell button | Outline variant, `border: 1px solid var(--down)` (`#dc2626`), text color `var(--down)`, transparent fill. Visually distinct from Buy so the two actions are never confused at a glance, while explicitly **not** using the shadcn `destructive` filled variant — selling is a normal, reversible trade with no confirmation step, not a destructive action requiring that visual weight. |

Rationale recorded for the checker: PLAN.md's palette names Purple "submit buttons" (singular color, no buy/sell distinction). This phase interprets that as the primary/filled submit action (Buy — the action a fresh $10,000-cash user takes first). Sell reuses the already-established `--down` semantic token (the same one driving downtick price flashes and the disconnected-status dot) rather than inventing a third color, keeping the palette closed. This is a deliberate, documented choice, not an oversight — flag for confirmation if the checker disagrees.

**Semantic status palette** (unchanged from Phase 1, reused — not reintroduced):

| State | Value | Usage |
|-------|-------|-------|
| Up | `#16a34a` | Positions-table unrealized P&L and % change when positive; positions-table row's "gain" indication. Same token driving Phase 1's uptick price flash. |
| Down | `#dc2626` | Positions-table unrealized P&L and % change when negative; Sell button outline/text (above). Same token driving Phase 1's downtick price flash and disconnected dot. |

Accent Yellow `#ecad0a` (PLAN.md's third brand color) remains unused through Phase 2 — still reserved for the Phase 4 AI/chat highlight treatment, per Phase 1's UI-SPEC note. Recording again here so Phase 3 doesn't reintroduce it inconsistently.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | "Buy" (filled, primary submit) / "Sell" (outline, secondary submit) — trade-bar buttons, both disabled until a valid ticker + whole-number quantity ≥ 1 is entered |
| Empty state heading | "No open positions" |
| Empty state body | "Buy shares from the trade bar above to open your first position." |
| Error state — insufficient cash (PORT-04) | "Not enough cash — this trade costs more than your $X,XXX.XX available." (X figure interpolated from live cash balance) |
| Error state — overselling (PORT-05) | "You only own N shares of TICKER." (N/TICKER interpolated from the current position) |
| Error state — untradable ticker (D-02) | "TICKER isn't on your watchlist — trade one of the tickers shown above." |
| Error state — malformed input (client-side, before any request) | "Enter a ticker and a whole number of shares." |
| Error state — portfolio/positions fetch failure | No dedicated banner; table keeps its last successfully loaded rows (see UI Considerations below) — same resilience pattern as Phase 1's SSE disconnect handling, no new copy needed |
| Destructive confirmation | Not applicable — trades are instant-fill market orders with no confirmation dialog by explicit design (PLAN.md §3, §9; D-01–D-04). This remains true for every trade regardless of size. |

All four trade-bar error strings render inline, near the trade bar, and clear automatically the moment the user changes ticker or quantity to a new value (D-04) — never a toast, never a modal.

## UI Considerations

> Populated by the ui-phase UI-consideration probe (Step 9.5) and lifted by plan-phase's
> `## UI Considerations` lift rule via the identical rule as SPEC `## Edge Coverage`. Shape-rooted UI *state*
> coverage (empty / loading / error / populated / partial / overflow / zero-one-many / long-text).
> Empty-state and error-state COPY live in `## Copywriting Contract` above — this section covers
> state coverage and REFERENCES those rows rather than restating the copy (de-dup).

> Element classification: trade bar → `form`; positions table → `list-collection`; header total
> value + cash figure → `static-content`, overridden to also raise `loading`/`error` (same
> propose-then-confirm override Phase 1 applied to the connection indicator — an async-backed
> numeric display is exactly a loading/error surface, not just static text). 16 applicable
> considerations resulted.

Applicable state considerations resolved: 12 covered, 4 backstop, 0 unresolved

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | trade bar (form) | ✅ covered | Initial state: ticker and quantity inputs empty, no error text shown, Buy/Sell present but disabled until both fields hold valid values |
| loading | trade bar (form) | 🧪 backstop | Buy/Sell buttons disable for the duration of an in-flight trade request, preventing a double-submit; no spinner text beyond the disabled state |
| error | trade bar (form) | ✅ covered | Insufficient-cash, overselling, and untradable-ticker rejections render as inline text near the trade bar (Copywriting Contract rows) and clear automatically on the next input change (D-04) |
| partial | trade bar (form) | 🧪 backstop | Submitting with only one of ticker/quantity filled is blocked client-side before any request, showing "Enter a ticker and a whole number of shares." |
| long-text | trade bar (form) | ✅ covered | Ticker input only accepts symbols already on the watchlist (≤5 characters, D-02) — no arbitrary-length ticker text is possible, so no truncation/wrap handling is needed |
| empty | positions table (list-collection) | ✅ covered | Zero positions renders the empty-state heading/body from the Copywriting Contract instead of an empty table |
| loading | positions table (list-collection) | ✅ covered | Before the first `/api/portfolio` fetch resolves, the table renders skeleton rows (same shadcn `Skeleton` pattern as Phase 1's watchlist), not a blank table |
| error | positions table (list-collection) | 🧪 backstop | On a portfolio fetch failure, the table keeps its last successfully loaded rows rather than clearing, matching the SSE resilience precedent from Phase 1 |
| populated | positions table (list-collection) | ✅ covered | A populated table shows one row per open position: ticker, quantity, avg cost, current price, unrealized P&L (colored via the up/down tokens), and % change |
| partial | positions table (list-collection) | ✅ covered | A sell that reduces a position to exactly zero shares removes that row immediately (Claude's Discretion resolution, `02-CONTEXT.md`) rather than showing a zero-quantity row |
| overflow | positions table (list-collection) | ✅ covered | Quantity, avg cost, price, P&L, and % change all render in fixed-width `tabular-nums` columns, matching the watchlist's numeric-overflow handling from Phase 1 |
| zero-one-many | positions table (list-collection) | ✅ covered | The table shows 0 (empty state), 1, or up to 10 rows — bounded by the watchlist's fixed ticker count (D-02); no pagination or truncation needed at this ceiling |
| loading | header total value + cash (static-content, overridden) | ✅ covered | Before the first `/api/portfolio` fetch resolves, the header total-value and cash figures render the Phase 1 `Skeleton` placeholder rather than flashing `$0.00` |
| error | header total value + cash (static-content, overridden) | 🧪 backstop | If the portfolio fetch fails, the header retains its last successfully loaded total value and cash figures rather than clearing to zero, matching the SSE resilience precedent |
| overflow | header total value + cash (static-content) | ✅ covered | Total value and cash format with the same thousands-separator numeric utility as watchlist prices (`formatPrice`), so large values never wrap the header layout |
| long-text | header total value + cash (static-content) | ✅ covered | Both figures are fixed-format currency numbers, not user-generated text — no long-text handling required |
