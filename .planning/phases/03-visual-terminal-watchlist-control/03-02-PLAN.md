## Phase Goal

**As a** trader watching a simulated portfolio, **I want to** see my whole portfolio at a glance and curate which tickers the terminal tracks, **so that** the terminal shows me what I care about and how I am doing without reading numbers row by row.

<objective>
Give total portfolio value a history and put it on screen: every trade records a snapshot atomically with itself, a background task records one every thirty seconds regardless of whether a browser is open, and a Recharts line chart plots the series.

Purpose: PORT-09 and D-01. This is the only capability in Phase 3 that needs durable server-side data — the sparklines and the main chart accumulate client-side from the stream, but a value-over-time chart must survive a page reload, which only a table can do.
Output: `record_portfolio_snapshot` and `get_portfolio_history` in the portfolio service, a snapshot write inside `execute_trade`'s transaction, `GET /api/portfolio/history`, the `SnapshotWriter` background task wired into the app lifespan, and the `PnlChart` component.
</objective>

**Snapshot write inside the trade transaction — `backend/app/portfolio/service.py`.**
Add `SNAPSHOT_HISTORY_LIMIT = 1000` as a module constant and three functions.

`_positions_value(conn, cache) -> float` — a private helper reading `SELECT ticker, quantity FROM positions WHERE user_id = ?` on the supplied connection and summing `quantity * cache.get(ticker).price` for every position whose ticker has a cached price, skipping the rest. This is the same formula and the same price source `get_portfolio` already uses; a snapshot that valued only the traded ticker would silently drift from the true portfolio value every time another position moved, which is the whole failure this helper prevents.

`_insert_snapshot(conn, total_value, recorded_at) -> None` — `INSERT INTO portfolio_snapshots (id, user_id, total_value, recorded_at) VALUES (?, ?, ?, ?)` with `uuid.uuid4().hex`, bound through `?` placeholders like every other statement in this module.

Inside `execute_trade`, immediately after `_write_cash_balance(conn, new_cash_balance)` and before the `COMMIT`, compute `total_value = new_cash_balance + _positions_value(conn, cache)` and call `_insert_snapshot(conn, total_value, executed_at)`. Reuse the `executed_at` string already computed for the trade row so the trade and its snapshot carry the identical timestamp. Putting the write here rather than in the HTTP handler is deliberate and load-bearing: the module docstring already promises that Phase 4's chat flow will import and call `execute_trade` directly, bypassing the route, so a snapshot written at the route layer would be silently skipped by every chat-initiated trade. Sharing the open transaction also means a rolled-back trade leaves no orphan snapshot.

`record_portfolio_snapshot(cache: PriceCache) -> float` — the standalone recorder Task 2's background writer calls. Open its own `connect()` inside `contextlib.closing`, read cash with `_read_cash_balance`, add `_positions_value(conn, cache)`, insert one snapshot stamped `datetime.now(UTC).isoformat()`, commit, and return the recorded total. It takes no connection argument precisely so a caller outside a request can use it.

`get_portfolio_history(limit: int = SNAPSHOT_HISTORY_LIMIT) -> list[dict]` — return the most recent `limit` snapshots in chronological order as dicts with `total_value` and `recorded_at`. Select the newest rows descending by `recorded_at` then `rowid`, bounded by the limit, and re-order the result ascending by the same two keys before returning; the `rowid` tie-break is what keeps two snapshots recorded in the same instant — the interval writer and a trade landing together — in a stable, deterministic order rather than an arbitrary one. Both rows persist independently; the table is append-only and nothing merges or de-duplicates them. Zero rows returns an empty list, never a synthesized starting point.

Add `record_portfolio_snapshot` and `get_portfolio_history` to `backend/app/portfolio/__init__.py`'s exports.

**Module placement.** `03-RESEARCH.md`'s recommended structure suggested `backend/app/market/snapshot_feed.py`. Place it at `backend/app/portfolio/snapshot_feed.py` instead. The market package is the lower layer — the cache and the feed know nothing about money — and putting a module that imports the portfolio service inside `market/` would invert that dependency. **`SnapshotWriter` — `backend/app/portfolio/snapshot_feed.py`.**
Module constant `SNAPSHOT_INTERVAL_SECONDS = 30.0` and a module logger, matching the market feed's conventions.

Constructor `SnapshotWriter(cache: PriceCache, interval: float = SNAPSHOT_INTERVAL_SECONDS, record: Callable[[PriceCache], float] = record_portfolio_snapshot)`. The `record` callable is injected with a default rather than imported and called directly so the lifecycle can be tested against a counting fake with no database at all — the same reason `MarketFeed` takes its source and its ticker callable as arguments.

`start()` raises `RuntimeError` when a task is already running and not done, then creates the loop task. Starting twice would leak the first task, which would keep writing snapshots alongside the new one — the identical failure the market feed guards against.

`stop()` cancels the task, awaits it, swallows the resulting cancellation, and clears the handle.

`_run()` is a `while True` loop that sleeps the interval FIRST and records after. Sleeping first matches the promise the empty-state copy makes to the user — the first snapshot appears within thirty seconds — instead of firing one at startup that the user never asked for.

`_tick()` calls the recorder through `run_in_threadpool` because the recorder opens a synchronous SQLite connection and must not block the event loop that is also driving the price feed and every open SSE stream. Re-raise `asyncio.CancelledError`; log any other exception and continue, so one bad write never kills the only task recording history.

Export `SnapshotWriter` and `SNAPSHOT_INTERVAL_SECONDS` from `backend/app/portfolio/__init__.py`.
